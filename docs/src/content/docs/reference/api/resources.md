A resource is something this server runs beside the printers. The kinds are
storage, database, event sink, printer driver, camera, history provider,
authenticator, and link to another server. Each is an instance of a kind,
named by an operator, with a declaration saying how to build it.

Declarations come from two places. The operator's configuration file is one,
and the API writes the other, an overlay the machine owns. The supervisor
builds every instance from the merged declarations, restarts one that
fails, and reports what it observes. A change of state is published as
`com.prusa.connect.resource.state.changed`. An instance from the operator's
file is read here and never written here. Every write needs the ETag of what
you last read in `If-Match`, or `If-None-Match: *` to create, because the
file has another writer. Reading takes `view_resource`, writing
`configure_resource` and restarting `operate_resource`, each on the kind.

A connector endpoint is an address this server dials, for a printer that
cannot dial in.

## Which operation to call {#which-operation}

| you want to | call |
|---|---|
| see what is running and how each instance is doing | [`list-resources`](#list-resources), [`get-resource`](#get-resource) |
| add, change or remove an instance | [`put-resource`](#put-resource), [`delete-resource`](#delete-resource) |
| retry a failed sink or a dropped connection now | [`restart-resource`](#restart-resource) |
| tell this server to dial a printer, or to stop | [`put-connector-endpoint`](#put-connector-endpoint), [`list-connector-endpoints`](#list-connector-endpoints), [`delete-connector-endpoint`](#delete-connector-endpoint) |
| see how much each module has stored | [`list-state-namespaces`](#list-state-namespaces) |
| generate a client for a module's own routes | [`get-module-openapi`](#get-module-openapi) |

A `201` from `put-connector-endpoint` says the address is stored and nothing
about the printer. Watch the event stream, or read the devices page, for
its arrival. `dry_run=true` validates a write without touching the file.

### `install-module` {#install-module}

`POST /api/v1/modules`. Install a module.

Stages a release, reads its manifest, holds the version to the range that was asked for, checks this core is one the module runs on, verifies the digests and writes the declaration into the machine-owned overlay. It is the `module add` command over HTTP, through the same functions and with the same refusals, so a page can install without shell access.

Nothing is written until every check has passed, so a refusal leaves the deployment exactly as it was. Without `approve` the module is installed and switched off, and the answer lists the permissions and the events the manifest asks for: read them, then install again with `approve` or switch the instance on with put-resource. A module the operator declared in their own configuration file is refused, because this server never writes that file.

The install takes effect at once. This server reads the declaration it has just written and converges on it: a module that was switched on starts here, its routes and its bundle are served, and list-resources carries the new instance with its `ui` object, so a page that reads the listing again draws the module's sidebar entry without anybody restarting anything. The answer waits a few seconds for the module to start. `state` says what it reached: `ready` when it is serving, `failed` with the cause in `reason` when it did not start, and `starting` when the start was still going when the wait ended. A module whose settings are missing or refused is `failed`, and the install itself still succeeded: write the settings with put-resource, which starts the module again. `running` is true only when the module is serving, and `restart` is true only when this server still has to be restarted to pick the declaration up.

With no `from`, the release is the one the configured marketplace offers for `module` at exactly `version`, and its digest is the marketplace's. Every fetched release is hashed while it is written and refused with MODULE_DIGEST_MISMATCH when it differs from the stated digest, before anything is unpacked. A `from` URL takes `sha256`. A download is https, and so is every redirect it follows. It never connects to this machine or the local network, except to the port of a marketplace configured on loopback for local development. A download that fails answers MODULE_DOWNLOAD_FAILED, with the same detail whatever the address answered.

With `approve`, the manifest is held to what the operator was shown: what the marketplace lists for the release, and `expect` when the request carries it. A manifest asking for anything beyond either is refused with MODULE_REQUESTS_CHANGED. A release whose name another module already holds is refused with MODULE_NAME_TAKEN.

While the operator's core.modules_enabled is false, every install and every update is refused with MODULES_DISABLED, and in safe mode SAFE_MODE, before anything is read or downloaded.

With `approve`, the install writes the module's grants into the authorization graph, the same grants `module add -approve` writes. A module that asks for observe gets the viewer role on the organization, so it reads every printer. The grants are written as the caller, so the caller needs the admin role on the organization, and an install the graph would refuse writes nothing. The same role is needed whenever `approve` records what the module may do as itself, even a permission no grant answers, `check_absent_people` and `list_people`. `approved` lists what was written and `withheld` what was not.

A reinstall takes back each grant the old declaration justified and the new manifest no longer asks for, and it is refused before anything is written when the caller could not take one back. The graph does not record who wrote a grant, so a grant an administrator wrote by hand that is the same as one of those is taken back too. Installs and removals of modules run one at a time.

Installing over an installed module is the update: the running process is stopped before its files are replaced. With `approve`, an update keeps what the operator decided: a permission or an event they took away stays away, a records room they set is kept unless `records_mib` names another, and `added` lists what the release asks for that the one before did not.

An update is kept only when the new release starts. The release it replaces is kept aside until then, and the answer waits up to a minute, because a module may migrate a database of its own before it reports ready. A new release that fails to start, such as one whose migration failed or one older than its database allows, is taken back: the old files, declaration and grants return, the old release runs again, and the answer is MODULE_UPDATE_ROLLED_BACK with the cause in reason. A migration that fails is undone whole, so the database is as it was. `schema_version` and `migrations` say what a start that succeeded did to the module's own database.

It takes configure_resource on the resource kind the manifest declares, which is the permission to administer that part of this server's configuration. Naming `from` takes the admin role on the organization.

- credential: bearer token. The client method is `installModule`
- request body: `application/json` (`ModuleRelease`), required
- response `201`: Created, `application/json` (`ModuleInstallation`)
- errors: `400`, `401`, `403`, `404`, `409`, `422`, `500`, `501`, `502`, each a [problem document](../../error-codes.md)
