A vocabulary is a closed set this build behaves by. There is one each for
error codes, event types, the capability keys a driver declares, resource
kinds, the authorization model and the linked extensions. A client reads one to turn a token into a sentence, or to check a
name before sending it.

The sets are read from the same tables the server enforces with, so a code
this endpoint does not list cannot leave this process. Most are fixed per
build and identical in every deployment of it. Those take no credential
and can be cached. Device
states are the exception: they describe what this deployment installed, so
two servers on one release answer differently, and the operation takes a
token. The pages [error codes](../../error-codes.md),
[event types](../../event-types.md) and
[authorization vocabulary](../../authorization-vocabulary.md) are generated
from the same registries and describe the release. These operations
describe the running process.

## Which operation to call {#which-operation}

| you want to | call |
|---|---|
| find every vocabulary and its version | [`list-vocabularies`](#list-vocabularies) |
| turn an error `code` into text for a person | [`get-error-code-vocabulary`](#get-error-code-vocabulary) |
| turn a device `issues` token into a sentence and an action | [`get-device-issue-vocabulary`](#get-device-issue-vocabulary) |
| know which event `type` values exist and how each is queued | [`get-event-type-vocabulary`](#get-event-type-vocabulary) |
| know which actions, relations and grant shapes exist | [`get-authorization-vocabulary`](#get-authorization-vocabulary) |
| render a printer's states and the verb behind each move | [`get-device-state-vocabulary`](#get-device-state-vocabulary) |
| turn a device `model` into a product name and an icon | [`get-device-model-vocabulary`](#get-device-model-vocabulary) |
| see what a driver may declare, or what an operator may configure | [`get-capability-vocabulary`](#get-capability-vocabulary), [`get-resource-kind-vocabulary`](#get-resource-kind-vocabulary), [`get-extension-vocabulary`](#get-extension-vocabulary) |

A verb named in the state vocabulary is not permission to send it. The
server decides that on the request itself.

### `get-authorization-vocabulary` {#get-authorization-vocabulary}

What a caller can perform, what those things are performed on, the edges that join them, and every shape a stored grant may take. It also carries the verb table: every device kind this build carries and every verb of it, with the class the verb takes and any marking that puts it in the dangerous tier. ### `get-device-model-artwork` {#get-device-model-artwork}

`GET /api/v1/vocabularies/device-models/{model}/artwork`. A drawing of a device model, from the driver that reaches it.

The drawing a driver declared for a model the web app has no drawing of its own for. The `artwork` member of a row in `get-device-model-vocabulary` links here, and only a row that carries it has one. A model with no drawing answers 404 with core.validation/RESOURCE_NOT_FOUND.

The entity tag is a digest of the drawing, and a client that sends it back is answered 304 with no body while its copy is current. A browser runs nothing from the answer. It carries `X-Content-Type-Options: nosniff` and a Content-Security-Policy that lets the browser load and run nothing, because an SVG is a document it would otherwise run when opened alone.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `model` | path | `string` | yes | The machine's own spelling, as the model member of a device-model row carries it. |
| `If-None-Match` | header | `string` | no | The entity tag of the drawing this client already has. A drawing with the same tag answers 304 with no body. |

- credential: none, the request is sent without a token. The client method is `getDeviceModelArtwork`
- request body: none
- response `200`: The drawing, in the type the driver declared, `image/png` (`binary`) or `image/svg+xml` (`binary`) or `image/webp` (`binary`)
- errors: `304`, `404`, `422`, `500`, each a [problem document](../../error-codes.md)

This operation has no sample: one SVG, PNG or WebP drawing, for the same reason the camera's still image is.

### `get-device-model-vocabulary` {#get-device-model-vocabulary}

`GET /api/v1/vocabularies/device-models`. The device models this build can name.

Every model this build knows, each with the machine's own spelling, the name the product is sold under, who makes it, and a key to map to an icon. A device record carries the machine's spelling in `model` and nothing else, so this is what turns `CoreOneL_INDX` into a name a person reads and a picture to put beside it.

The icon key names a family rather than a model. Machines in one family look alike, so a page maps a handful of keys onto a handful of drawings instead of carrying one per model, and a key it has no drawing for is answered with a generic device.

It is the set this binary carries and not a catalogue of everything Prusa makes: the Prusa models a capability profile covers and the models a driver composed into the build declared, in one list, each under its own dialect. A machine reporting a model with no row here still connects and is still listed: the capability profile is what a model decides, and a device that matched none runs on the driver's baseline. The model member of `list-devices` filters on the same spelling.

- credential: none, the request is sent without a token. The client method is `getDeviceModelVocabulary`
- request body: none
- response `200`: OK, `application/json` (`DeviceModelsOutputBody`)

### `get-device-state-vocabulary` {#get-device-state-vocabulary}

`GET /api/v1/vocabularies/device-states`. The states each device kind's adapter declared.

Every state a device of each kind reports, what to show for it, the verbs it accepts in that state, and every move between two of them with the verb that causes it. A move a device makes on its own names no verb. There is one entry per connector type, and a device's driver names the instance its entry lists under connectors. This answer is what this deployment installed rather than what the build ships, so two servers on one release answer differently and a client reads it per server. That is why this vocabulary takes an identity and the others do not. A verb named here is not permission to send it: the server decides that on the request itself, and this list is a hint a client renders from.

- credential: bearer token. The client method is `getDeviceStateVocabulary`
